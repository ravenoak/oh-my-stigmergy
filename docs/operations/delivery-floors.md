# Delivery floors (FR-10.x)

Adapted from `stigmergy-stack-v2/delivery-floors.md`, reduced to what this repo doesn't already
have: actions-pinning, secret-scanning, and branch-protection tooling exist and are documented
elsewhere (see [github-branch-protection.md](github-branch-protection.md),
[`scripts/verify-actions-pinned.sh`](../../scripts/verify-actions-pinned.sh),
[`scripts/verify-no-secrets.sh`](../../scripts/verify-no-secrets.sh)). This doc covers the floors
added by [`docs/planning/orchestrator-implementation-plan.md`](../planning/orchestrator-implementation-plan.md)
Stage 3.

## Status: report-only

All three checks below **warn but never fail CI** today — they print a clear `WARN` line to the
`governance` job's log and exit `0` regardless of outcome. Set `DELIVERY_FLOORS_BLOCKING=1` in the
workflow step's `env:` to make a real violation fail the check; this is a **one-line change per
check**, deliberately deferred to a separate, explicitly reviewed PR rather than silently promoted
alongside unrelated work.

## Floor 1 — frozen test manifest (FR-10.1)

[`scripts/verify-frozen-test-manifest.sh`](../../scripts/verify-frozen-test-manifest.sh) +
[`devtools/frozen-test-manifest.json`](../../devtools/frozen-test-manifest.json) (`frozenPaths`: a
map of path → recorded SHA-256). If a PR changes a path registered in `frozenPaths` and its content
hash no longer matches, the check warns unless the PR carries the `test-amendment` label.

**Phase-keying is interim.** There is no ledger `phaseTransition` mark to key "implement phase" on
yet — the manifest's `frozenPaths` entries themselves are the phase declaration for now. Once the
human-as-orchestrator bridge (a later stage) publishes real phase marks, keying on those becomes
possible and this interim mechanism can be superseded.

The manifest ships with `frozenPaths: {}` — nothing is frozen yet. Populate it (with the recorded
hash of the file at freeze time) when a test file should stop changing silently.

## Floor 2 — lockfile freeze (FR-10.2)

[`scripts/verify-lockfile-freeze.sh`](../../scripts/verify-lockfile-freeze.sh) +
[`devtools/lockfile-freeze.json`](../../devtools/lockfile-freeze.json) (`pairs`: lockfile →
manifest). If a PR changes a lockfile (`uv.lock`, a package's `package-lock.json`) without also
changing its sibling manifest (`pyproject.toml`, `package.json`) in the same diff, the check warns
unless the PR carries the `deps-review` label — this catches unreviewed dependency drift (a
lockfile regenerated by tooling without an accompanying, deliberate manifest edit).

## Floor 3 — dependency allowlist (FR-10.3)

[`scripts/verify-dependency-allowlist.sh`](../../scripts/verify-dependency-allowlist.sh) +
[`devtools/dependency-allowlist.json`](../../devtools/dependency-allowlist.json). Diffs each
registered manifest's dependency names between the PR's merge-base and `HEAD`; any **newly added**
name not on the allowlist for its ecosystem (`pip` via `tomllib`, `npm` via the `package.json`
`dependencies`/`devDependencies`/`peerDependencies` keys) warns unless the PR carries the
`deps-review` label. Version bumps of already-allowed dependencies are not flagged — only genuinely
new package names.

## Fixture-PR test harness (FR-10.4)

[`tests/lib/fixture_pr.sh`](../../tests/lib/fixture_pr.sh) + [`tests/delivery_floors_contract.sh`](../../tests/delivery_floors_contract.sh).
None of the co-touch-style `verify-*.sh` scripts in this repo were previously testable outside a
real PR — they always resolve their own `repo_root` from their script location, then diff against
`origin/$GITHUB_BASE_REF`, which only exists in a real CI checkout. The harness stages a synthetic
git repo, fakes an `origin/$GITHUB_BASE_REF` ref (no real remote or network needed — only a git ref
named `refs/remotes/origin/<branch>` is ever resolved), copies the script-under-test into the
fixture so its `repo_root` resolves there, and drives it through `GITHUB_EVENT_NAME`/`GITHUB_BASE_REF`/`PR_LABELS`
exactly as the real workflow would. `tests/delivery_floors_contract.sh` uses it to exercise all
three floors above (violation/no-violation, report-only/blocking, with/without the escape label) and
includes a harness self-check against the pre-existing `verify-governance-doc-cotouch.sh`, proving
the harness faithfully reproduces real PR-diff behavior rather than just asserting what the new
scripts happen to do.

## Merge queue

Not enabled by this stage — enabling it is an operator action in GitHub's branch protection UI /
API, not a code change this repo makes on your behalf (per the "never silent CI edits" discipline).
See [github-branch-protection.md](github-branch-protection.md) for how required status checks are
applied; a merge queue is configured the same way (repository settings → branch protection rules →
merge queue), and requires the `allium-specs / check` status to remain the required check.
